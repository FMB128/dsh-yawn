{{- include "dsh-yawn.validate" . }}
The control plane is installed in {{ .Release.Namespace }}. It has no sandbox
pool of its own: sessions can be created and the Web UI works, but the first
tool call needs a runner. Set one up before using it —

  https://github.com/zhming0/dsh-yawn/blob/main/docs/installations.md

For sandboxes in this cluster, that is the sandbox pool; the
agent-sandbox v1.0.2 controllers are not installed by this chart:

  https://github.com/zhming0/dsh-yawn/blob/main/docs/runners/kubernetes.md

The pool reads one fixed name from this release: the `dsh-yawn-runner-config`
ConfigMap holding DSH_YAWN_CONTROL_PLANE_URL. The `dsh-yawn-registration-token`
Secret is created and kept current by the control plane itself, as soon as it
starts.

{{- if .Values.controlPlane.sandboxManager }}

This release owns the deployment base of the control plane's sandbox-manager
settings: the chart mounts them at /etc/dsh-yawn/sandbox-settings.yaml, and the
Web UI's Settings → Sandboxes page adds its own profiles and changes the
default and timers over that base. The profiles named in the values are locked
there. `helm upgrade` changes the base, and the pod restarts.

{{- else }}

No sandbox profile is configured. Point the control plane at a runner by setting
controlPlane.sandboxManager in your values file and running `helm upgrade`; the
runner setup pages below show the profile to add.

{{- end }}

{{- if .Values.oidc.enabled }}

The control plane reads its OIDC registration from the Secret
"{{ .Values.oidc.existingSecret }}" in {{ .Release.Namespace }}. If it does not
exist yet, create it — until then the pod cannot start:

  kubectl -n {{ .Release.Namespace }} create secret generic {{ .Values.oidc.existingSecret }} \
    --from-literal=OIDC_ISSUER=https://your-idp/realm \
    --from-literal=OIDC_CLIENT_ID=dsh-yawn-control-plane \
    --from-literal=OIDC_CLIENT_SECRET=…

Register this redirect URI with the identity provider:

  https://{{ .Values.oidc.hostname }}/dsh-yawn/auth/callback

The control plane signs users in itself; there is no auth proxy and no
/launch-token step. Its browser-session signing secret is created on the data
volume, so a pod restart does not sign everyone out.

{{- if eq .Values.service.type "LoadBalancer" }}
Once the Secret exists and the load balancer's address resolves for
{{ .Values.oidc.hostname }}, open

  https://{{ .Values.oidc.hostname }}/

and sign in through the identity provider.
{{- else }}
The control plane is exposed at Service/{{ include "dsh-yawn.fullname" . }}
(port {{ .Values.service.port }}) but not outside the cluster. Point an Ingress,
a Gateway API route, or a LoadBalancer Service of your own at it — the pod
labels (app.kubernetes.io/name, app.kubernetes.io/instance) are a stable target —
then open https://{{ .Values.oidc.hostname }}/. Whatever fronts it must serve
https and pass WebSockets and large RPC bodies; docs/control-plane.md has an
nginx-ingress example.
{{- end }}

{{- else }}

dsh is reachable over a port-forward only. In another terminal:

  kubectl -n {{ .Release.Namespace }} port-forward deploy/{{ include "dsh-yawn.fullname" . }} 3000:3000

Then open http://localhost:3000/launch-token — or take the tokenized URL from
the control plane log and open it directly:

  kubectl -n {{ .Release.Namespace }} logs deploy/{{ include "dsh-yawn.fullname" . }} | grep 'dsh web:'

{{- end }}

Add provider secrets (a GITHUB_TOKEN is also the Git credential for
github.com) from the Web UI's Settings → Secrets page, once you can reach the
UI.
